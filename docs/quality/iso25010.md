# Quality model (ISO/IEC 25010:2023)

This project uses the product quality model of ISO/IEC 25010:2023 to define
quality requirements and how each one is verified. Every pull request is reviewed
against this table (see the PR template).

Legend for verification: **UT** unit test, **IT** integration test
(`test/integration`), **CI** automated pipeline check, **RV** code/design review,
**DOC** documented behaviour.

## 1. Functional suitability

| Sub-characteristic | Requirement | Verification |
|--------------------|-------------|--------------|
| Functional completeness | Create, list, start, stop, restart, re-create, delete agent boxes; interactive console; resource usage display. | IT, RV |
| Functional correctness | Resource limits passed by the user are clamped to configured maxima; names validated. | UT (`broker`) |
| Functional appropriateness | No AI agent is pre-installed; box is a plain Linux console the user controls. | DOC |

## 2. Performance efficiency

| Sub-characteristic | Requirement | Verification |
|--------------------|-------------|--------------|
| Time behaviour | Agent creation (image present) < 3 s; console attach < 500 ms on N150. | IT (timed), RV |
| Resource utilisation | Idle box < 5 MiB RSS; each service < 32 MiB RSS; service image < 30 MiB. | IT, CI (image size) |
| Capacity | ≥ 20 concurrent boxes on a default Docker engine (network pool). | DOC |

## 3. Compatibility

| Sub-characteristic | Requirement | Verification |
|--------------------|-------------|--------------|
| Co-existence | Only touches Docker objects labelled `dockerbox.managed=true` + own instance label; multiple instances possible. | UT, IT |
| Interoperability | Docker Engine API ≥ 1.41 (Docker 20.10+), `linux/amd64` and `linux/arm64`; standard proxy env vars for tools in the box. | CI (multi-arch build), IT |

## 4. Interaction capability (usability)

| Sub-characteristic | Requirement | Verification |
|--------------------|-------------|--------------|
| Appropriateness recognizability | Layout follows the familiar "VM manager" pattern (sidebar list, power button, console). | RV |
| Learnability | First agent running within 2 minutes after install, following README. | DOC |
| Operability | Every action reachable with keyboard; works on tablet width (≥ 768 px) and phone (sidebar collapses). | RV |
| User error protection | Delete requires confirmation; "keep data" is the default. | RV |
| Inclusivity | English and German UI (browser language), text contrast ≥ 4.5:1, `aria` labels on icon buttons. | RV |
| Self-descriptiveness | Clear error messages from the broker are shown in the UI. | RV |

## 5. Reliability

| Sub-characteristic | Requirement | Verification |
|--------------------|-------------|--------------|
| Faultlessness | `go vet`, staticcheck, race detector in tests. | CI |
| Availability | Services restart automatically (`unless-stopped`), healthchecks; boxes survive dashboard restarts. | IT |
| Fault tolerance | Failed creation is rolled back (container and network removed); broker reconciles egress attachments. | UT, IT |
| Recoverability | Box data in named volumes; re-create from new image keeps data. | IT |

## 6. Security

| Sub-characteristic | Requirement | Verification |
|--------------------|-------------|--------------|
| Confidentiality | Boxes cannot reach host, LAN or each other; secrets never logged. | IT, UT, RV |
| Integrity | Container specs validated by policy before creation; no raw API passthrough. | UT |
| Non-repudiation | Structured logs for all lifecycle actions. | RV |
| Accountability | Each action logged with agent name and source. | RV |
| Authenticity | Password login, signed session cookies, CSRF protection. | UT |
| Resistance | Rate limiting, strict CSP, minimal images, dependency and image scanning. | UT, CI |

## 7. Maintainability

| Sub-characteristic | Requirement | Verification |
|--------------------|-------------|--------------|
| Modularity | Packages `dockerapi`, `broker`, `egress`, `web` with one-directional dependencies. | RV |
| Reusability | Egress filter and policy are independent packages. | RV |
| Analysability | Structured logging (`log/slog`, JSON), ADRs for decisions. | RV |
| Modifiability | `gofmt`, linters, conventional commits, CHANGELOG. | CI |
| Testability | Docker client behind an interface; policy and filter pure functions. | UT |

## 8. Flexibility (portability)

| Sub-characteristic | Requirement | Verification |
|--------------------|-------------|--------------|
| Adaptability | All limits, image, runtime, port configurable via env. | DOC |
| Scalability | Number of boxes limited only by host resources and network pool. | DOC |
| Installability | One `docker-compose.yml`, no host changes; ZimaOS metadata (`x-casaos`). | IT, RV |
| Replaceability | Box image can be swapped (`DOCKERBOX_AGENT_IMAGE`). | DOC |

## 9. Safety

| Sub-characteristic | Requirement | Verification |
|--------------------|-------------|--------------|
| Operational constraint | Hard resource limits keep the host responsive when an agent misbehaves. | IT |
| Risk identification | Threat model maintained with every security-relevant change. | RV |
| Fail safe | If the policy rejects a spec, nothing is created; proxy denies on resolution errors. | UT |
| Hazard warning | UI and docs warn that API keys inside a box are visible to the agent. | DOC |
| Safe integration | Agents can only reach the outside world through the egress proxy. | IT |
